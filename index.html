Q1.8 Domain 1 単一選択Single choice

単一の「オペレーションエージェント」がHRの問い合わせ、ITチケット、財務リクエストを処理している。このエージェントは35個のツールと、3ドメインすべてをカバーする6,000トークンのシステムプロンプトを持ち、機能が追加されるにつれてツール選択精度が低下してきた。ステークホルダーは次に調達（procurement）を追加したいと考えている。最も強く推奨すべきアーキテクチャはどれか。

  • Aルーターの背後で、焦点の絞られたツールセットを持つドメイン別エージェントに分割する
  • B今すぐ調達ツールを追加し、プロンプトの書き直しは次の四半期に計画する
  • Cエージェントを1つのまま維持し、全ドメインを詳しくカバーするためプロンプト長を倍増する
  • Dモデルが一般知識から回答しなくなるよう、毎回のリクエストで必ずツール利用を強制する

A single “operations agent” handles HR queries, IT tickets, and finance requests. It has 35 tools, a 6,000-token system prompt covering all three domains, and its tool-selection accuracy has been declining as capabilities were added. Stakeholders want to add procurement next. What is the strongest architectural recommendation?

  • ASplit it into domain-specific agents behind a router, each with a focused toolset
  • BAdd the procurement tools now and schedule a prompt rewrite next quarter
  • CKeep one agent but double the system prompt to cover every domain in detail
  • DForce a tool call on every single request so it stops answering from general knowledge
✔ 正解 / Correct: A
解説：正答: (A)。能力を追加するにつれてツール選択精度が低下するのは、単一エージェントが過負荷になる典型的な症状だ。HR・IT・financeにまたがる35個のツールと6,000トークンのプロンプトはモデルの正しいツール選択能力を薄め、procurementを追加すればさらに悪化する。ルーターまたはスーパーバイザーの背後でドメイン別エージェントに分割すれば、各エージェントは焦点の絞られたツールセットとプロンプトを持ち、選択精度が回復する。procurementは独立した新しいエージェントとなり、逼迫したエージェントへの追加負担ではなく単なる追加になる。 誤答の理由: (B)は今procurementを追加してプロンプト書き直しを先送りにするが、すでに性能を劣化させている過負荷そのものを悪化させる。(C)はプロンプト長を倍増させるが、指示は従いにくくなりこそすれ従いやすくはならず、35ツールの選択問題に何も手を打たない。(D)は毎リクエストでツール呼び出しを強制するが、失敗の誤診だ。問題は多すぎるツールから選ぶことで、モデルが一般知識から回答することではない。
Rationale: Correct answer: (A). Declining tool-selection accuracy as capabilities are added is the classic symptom of an overloaded single agent: 35 tools and a 6,000-token prompt spanning HR, IT, and finance dilute the model's ability to pick the right tool, and adding procurement would make it worse. Splitting into domain-specific agents behind a router or supervisor gives each agent a focused toolset and prompt, restoring selection accuracy; procurement then becomes a new, self-contained agent -- an addition, not an extra burden on a strained one. Why the others are wrong: (B) adds procurement now and defers the prompt rewrite, compounding the exact overload already degrading performance. (C) doubles the prompt length, which makes instructions harder to follow, not easier, and does nothing about the 35-tool selection problem. (D) forces a tool call on every request, which misdiagnoses the failure -- the problem is choosing among too many tools, not the model answering from general knowledge.
Q1.6 Domain 1 単一選択Single choice

ある文書トリアージ（振り分け）ソリューションが本番稼働して3か月になる。チームはレイテンシとコストのダッシュボードを持っているが、本番でモデルの分類が実際に正しいかを知る手段がない。このギャップを最も直接的に埋めるアーキテクチャ上の追加はどれか。

  • A分類精度は一般にモデル能力とともに向上するため、より大きなモデルを導入する
  • B日次のトークン消費が通常から逸脱した際に発報するアラート
  • Cルーティング指示が最新のままか確認するための、システムプロンプトの週次レビュー
  • D本番出力のサンプルをラベル付き評価データセットに送り込むフィードバックループ

A document-triage solution has been in production for three months. The team has latency and cost dashboards but no way of knowing whether the model’s classifications are actually correct in production. Which architectural addition most directly closes this gap?

  • AA larger model, since accuracy generally improves with model capability
  • BAn alert that fires when daily token consumption deviates from the norm
  • CA weekly review of the system prompt to confirm the routing instructions stay current
  • DA feedback loop that samples production outputs into a labelled evaluation set
✔ 正解 / Correct: D
解説：正答: (D)。チームはレイテンシとコストは見えているが、本番での正しさのシグナルがない。欠けているのは input->processing->output->feedback ループのフィードバック段階だ。本番出力のサンプルをラベル付き評価データセットに送り込む（下流の修正とユーザーシグナルを捕捉する）フィードバックループは、分類が正しいかを実際に測定し、品質を継時的に追跡して改善を駆動するデータを生む唯一の選択肢だ。 誤答の理由: (A)は精度が上がるという想定で大きなモデルに差し替えるが、正しさを測定せずにシステムを変えるだけで、依然として盲目のままだ。(B)はトークン消費の異常を警告するが、コストの監視であって分類の正しさではない。(C)はシステムプロンプトを週次でレビューするが、設定の最新性の検査であって本番出力の正しさではない。特定された欠落（本番でモデルが実際に正しいかを知ること）を埋めるのは(D)だけだ。
Rationale: Correct answer: (D). The team can see latency and cost but has no signal on correctness in production -- the missing element is the feedback stage of the input->processing->output->feedback loop. A feedback loop that samples production outputs into a labelled evaluation set (capturing downstream corrections and user signals) is the only option that actually measures whether classifications are right and creates the data needed to track quality over time and drive improvement. Why the others are wrong: (A) swaps in a larger model assuming accuracy will improve, but changes the system without ever measuring correctness -- you would still be blind. (B) alerts on token-consumption anomalies, which monitors cost, not whether classifications are correct. (C) reviews the system prompt weekly, which inspects configuration currency, not production output correctness. Only (D) closes the specific gap: knowing whether the model is actually right in production.
Q1.1 Domain 1 単一選択Single choice

ある物流会社は、Claudeに入荷貨物の見積もりを処理させたいと考えている。すべてのリクエストは同じ手順に従う。すなわち、メールから出荷情報を抽出し、レートカード（rate card）と照合して検証し、見積書を生成する。要件は安定しており、手順が変わることはない。最も適切なアーキテクチャパターンはどれか。

  • Aスーパーバイザーエージェントが専門エージェントに委任するマルチエージェントシステム
  • B各ステップを個別かつ順序化されたLLM呼び出しとして実行する固定ワークフロー
  • Cリクエストごとに自らアプローチを計画する、ツールアクセス付きの自律エージェント
  • Dすべての指示とレートカード全体を保持する単一のモノリシックなプロンプト

A logistics company wants Claude to process inbound freight quotes. Every request follows the same steps: extract shipment details from an email, validate them against a rate card, and generate a quote document. Requirements are stable and the steps never vary. Which architectural pattern is most appropriate?

  • AA multi-agent system with a supervisor agent delegating to specialist agents
  • BA fixed workflow of discrete, sequenced LLM calls, one per step
  • CAn autonomous agent that plans its own approach for each request
  • DA single monolithic prompt holding every instruction and the full rate card
✔ 正解 / Correct: B
解説：正答: (B)。このタスクは完全に決定論的である。すべての貨物見積もりは同一の3ステップ（出荷情報の抽出、レートカードとの照合による検証、見積書の生成）を辿り、要件は「安定しており手順が変わることはない」と明示されている。これは固定ワークフローの典型例で、各ステップを個別かつ順序化されたLLM呼び出しとして実装する。予測可能性（毎回同じ経路）、ステップ単位の監査可能性（抽出・検証・生成を個別に検査・記録できる）、デバッグの容易さ（障害を単一ステップに切り分けられる）が得られる。要件を満たす最も単純なパターンを選ぶのが設計の基本原則だ。 誤答の理由: (A)はスーパーバイザーと専門エージェントを導入するが、単一経路の固定タスクにはマルチエージェント協調（メッセージパッシング、委任、統合）のオーバーヘッドが不要だ。(C)はリクエストごとに自律計画を行うが、手順が変わらない以上計画すべきものがなく、レイテンシ・コスト・非決定性を増やすだけだ。(D)はすべてを単一のモノリシックなプロンプトに詰め込み、ステップ単位の制御と、抽出した出荷データを使用前に検証する能力を失い、エラー検出と監査が難しくなる。
Rationale: Correct answer: (B). The task is completely deterministic: every freight quote follows the identical three steps -- extract shipment details, validate against the rate card, generate the quote -- and requirements are explicitly stable and never varying. That is the textbook case for a fixed workflow, with each step as a discrete, sequenced LLM call. It gives predictability (the same path every time), per-step auditability (extraction, validation, and generation can each be inspected and logged), and easy debugging (a failure isolates to one step). Choosing the simplest pattern that satisfies the requirement is a core design principle. Why the others are wrong: (A) adds a supervisor and specialist agents, imposing multi-agent coordination overhead (message passing, delegation, merging) that a single-path task gains nothing from. (C) gives the model autonomous per-request planning, but nothing varies, so it only adds latency, cost, and non-determinism. (D) collapses everything into one monolithic prompt, sacrificing step-level control and the ability to validate extracted shipment data before it is used, making errors harder to catch and output harder to audit.
Q1.7 Domain 1 単一選択Single choice

ある小売業者の商品カタログ、価格、プロモーションは毎日変わる。チームはこの情報を使ってClaudeに顧客の質問へ回答させたいと考えており、モデルにどうアクセスを与えるかを議論している。最も適切なアプローチはどれか。

  • A現在のカタログでモデルをファインチューニングし、四半期ごとにこれを繰り返す
  • Bライブカタログに対するリトリーバルでクエリ時にモデルを拡張する
  • Cカタログ全体を毎リクエストのコンテキストウィンドウに貼り付ける
  • Dベースモデルの知識に頼り、価格は変動する可能性があるという免責文を添える

A retailer’s product catalogue, pricing, and promotions change daily. The team wants Claude to answer customer questions using this information and is debating how to give the model access to it. Which approach is most appropriate?

  • AFine-tune a model on the current catalogue and repeat this each quarter
  • BAugment the model with retrieval over the live catalogue at query time
  • CPaste the entire catalogue into the context window on every request
  • DRely on the base model's knowledge and add a disclaimer that prices may vary
✔ 正解 / Correct: B
解説：正答: (B)。カタログ、価格、プロモーションは毎日変わるため、モデルは常に現在のデータから回答しなければならない。リトリーバル拡張（RAG）が典型的な適合だ。クエリ時にライブカタログをリトリーバルするので、回答は再学習なしに当日のデータを反映し、カタログ全体をコンテキストに保持する必要もない。 誤答の理由: (A)は四半期ごとにファインチューニングするが、毎日変わるデータは学習実行の翌日には陳腐化する。ファインチューニングは振る舞いや形式を教えるもので、変動する事実を教えない。(C)はカタログ全体を毎リクエストに貼り付けるが、トークン面でコストが高く、カタログの拡大でスケールせず、更新の仕組みも必要になる。(D)はベースモデルの知識と免責文に頼るが、単に誤った価格を提示して免責文で覆おうとするだけで、顧客向けの価格提示としては許容できない。
Rationale: Correct answer: (B). The catalogue, pricing, and promotions change daily, so the model must always answer from current data. Retrieval augmentation (RAG) is the canonical fit: the model retrieves the live catalogue at query time, so answers reflect today's data with no retraining and no need to hold the entire catalogue in context. Why the others are wrong: (A) fine-tunes quarterly, but data that changes daily is stale within a day of any training run -- and fine-tuning teaches behaviour/format, not volatile facts. (C) pastes the full catalogue into every request, which is costly on tokens, will not scale as the catalogue grows, and still needs a refresh mechanism. (D) relies on base-model knowledge plus a disclaimer, which simply serves wrong prices and hopes the disclaimer covers it -- unacceptable for customer-facing pricing.
Q1.4 Domain 1 単一選択Single choice

ある保険金請求処理ソリューションは、intake（受付）、fraud screening（不正スクリーニング）、policy validation（証券検証）、payout calculation（支払額計算）の4つの専門エージェントを使う。ビジネス上、すべての決定について完全で順序付けられた監査証跡が必要であり、先行エージェントが例外を検出した場合は後続エージェントを実行してはならない。これらの要件を最もよく満たすオーケストレーション戦略はどれか。

  • A各専門エージェントを順番に実行し、結果を記録し、例外発生時に停止するスーパーバイザー
  • B各エージェントが次に実行するエージェントを選ぶピアツーピアの受け渡し
  • C4つの専門エージェントを並列実行し、最後にそれぞれの出力を統合する
  • Dすべてのエージェントが監視し日和見的に応答する共有メッセージボード

A claims-processing solution uses four specialist agents: intake, fraud screening, policy validation, and payout calculation. The business requires a complete, ordered audit trail of every decision, and later agents must not run if an earlier agent flags an exception. Which orchestration strategy best satisfies these requirements?

  • AA supervisor that runs each specialist in order, records outcomes, and halts on exceptions
  • BPeer-to-peer handoffs where each agent picks which agent runs next
  • CRunning all four specialist agents in parallel and merging their separate outputs at the very end
  • DA shared message board that all agents monitor and answer opportunistically
✔ 正解 / Correct: A
解説：正答: (A)。要件は3つの厳格な制約を挙げている。完全で順序付けられた監査証跡、4つの専門エージェントの厳密な順序実行、そして先行エージェントが例外を検出した場合の即時停止だ。スーパーバイザー/オーケストレーターは設計上この3つをすべて満たす。intake、fraud screening、policy validation、payout calculationを固定順で呼び出し、各結果を中央の一点から記録し（順序付き監査証跡）、例外発生の瞬間にチェーンを停止する。中央集権的な制御こそが「順序」と「例外時停止」を願望から保証へ変える。 誤答の理由: (B)は各エージェントが次を選ぶピアツーピアの受け渡しで、順序と停止が保証された性質ではなく創発的になる。規制対象の保険金処理が依拠できない。(C)は4エージェントを並列実行し、例外検出後に後続段階を走らせない規則に真っ向から違反する（fraud screening完了前にpayoutが計算されうる）。(D)はエージェントが日和見的に応答する共有メッセージボードで、順序と例外処理を運任せにし、順序の唯一のオーソリタティブな記録が存在しない。
Rationale: Correct answer: (A). The requirements name three hard constraints: a complete, ordered audit trail; strict sequencing of the four specialist agents; and a hard stop if any earlier agent flags an exception. A supervisor/orchestrator satisfies all three by design -- it invokes intake, fraud screening, policy validation, and payout calculation in fixed order, records each outcome from one central point (the ordered audit trail), and halts the chain the moment an exception is raised. Centralised control turns 'ordering' and 'stop on exception' from hopes into guarantees. Why the others are wrong: (B) uses peer-to-peer handoffs where each agent chooses the next, making order and halting emergent rather than guaranteed -- which a regulated claims process cannot rely on. (C) runs all four agents in parallel, directly violating the rule that later stages must not run once an exception is flagged (payout could be computed before fraud screening finishes). (D) is a shared message board where agents respond opportunistically, leaving sequencing and exception handling to chance with no single authoritative record of order.
Q1.9 Domain 1 複数選択（2つ）Multiple response (choose 2)

あるアーキテクトが、新しいソリューションについて固定ワークフローと自律エージェントのどちらにするか決めようとしている。固定ワークフローを最も強く支持する問題の特徴を2つ選べ。

  • A入力が予測不能な形式で届き、ケースごとの動的な処理を要する
  • B処理ステップが事前に既知で、すべてのリクエストで同一である
  • C複数の候補となる解決経路を創造的に探索することがタスクに有益である
  • Dビジネス上、各ステップを個別に監査可能かつ再現可能にする必要がある
  • E予期せぬツール障害からモデルが自律的に回復することをチームが望んでいる

An architect is deciding between a fixed workflow and an autonomous agent for a new solution. Which TWO characteristics of the problem most strongly favour the fixed workflow?

  • AInputs arrive in unpredictable formats that require dynamic, case-by-case handling
  • BThe processing steps are known in advance and identical for every request
  • CThe task benefits from creative exploration across multiple candidate solution paths
  • DEach step must be individually auditable and reproducible for the business
  • EThe team wants the model to recover autonomously from unexpected tool failures
✔ 正解 / Correct: B、D
解説：正答: (B) と (D)。固定ワークフローが好ましいのは、処理ステップが事前に既知で、すべてのリクエストで同一の場合（B）——その予測可能性こそ固定シーケンスが表現するもの——と、各ステップを個別に監査可能かつ再現可能にする必要がある場合（D）——個別かつ順序化されたステップ群がこれを直接提供する——だ。両者を合わせると、安定し制御可能で検査可能なパイプラインが描かれる。 誤答の理由: (A)（入力が予測不能な形式で届き動的処理を要する）はエージェントの自律性を支持する。動的処理はエージェントのplan-act-observeループが提供するもので、固定シーケンスではない。(C)（複数の解決経路の創造的探索から利益を得る）は動的な計画と探索に報いるもので、単一の固定経路の対極だ。(E)（予期せぬツール障害からの自律的回復）は障害を観察し適応できるエージェントを求めるもので、事前固定シーケンスの対極だ。
Rationale: Correct answers: (B) and (D). A fixed workflow is favoured when the processing steps are known in advance and identical for every request (B) -- that predictability is exactly what a fixed sequence encodes -- and when each step must be individually auditable and reproducible (D), which a discrete, ordered set of steps provides directly. Together these describe a stable, controllable, inspectable pipeline. Why the others are wrong: (A) (inputs arrive in unpredictable formats needing dynamic handling) argues for agentic autonomy, since dynamic handling is what an agent's plan-act-observe loop provides, not a fixed sequence. (C) (benefits from creative exploration of multiple solution paths) rewards dynamic planning and exploration, the opposite of a single fixed path. (E) (autonomous recovery from unexpected tool failures) calls for an agent that can observe a failure and adapt -- again the opposite of a pre-fixed sequence.
Q1.10 Domain 1 複数選択（2つ）Multiple response (choose 2)

あるチームが、複雑なデューデリジェンス（due-diligence）タスクについて、単一の拡張エージェントではなくマルチエージェント設計が正当化されるかを評価している。複数エージェントが妥当であることを最も強く示すタスクの特徴を2つ選べ。

  • A全体のリクエスト量が、特に繁忙期には本番で非常に高くなると見込まれる
  • Bプロジェクト予算が複数エージェントを余裕をもって賄えるほど潤沢である
  • C個別のサブタスクが、単一エージェントを過負荷にする異なる専門性とツールを要する
  • D利用可能な中で最も高度なアーキテクチャをステークホルダーが求めている
  • E独立した複数のサブタスクを並列実行し、エンドツーエンドの時間を短縮できる

A team is assessing whether a complex due-diligence task justifies a multi-agent design instead of a single augmented agent. Which TWO characteristics of the task most strongly indicate that multiple agents are warranted?

  • AThe overall request volume is expected to be very high, especially during seasonal peaks
  • BThe project budget is large enough to comfortably afford multiple agents
  • CDistinct sub-tasks need different specialisations and tools that overload one agent
  • DStakeholders have asked for the most sophisticated architecture available today

Q7.3 Domain 7 単一選択Single choice

本番（production）の agent が、一部のリクエストで予期しないアクションを取り始めた。オンコールのエンジニアの本能は、すぐにシステムプロンプトを書き直すことである。まず何をすべきか？

  • A影響を受けたsessionのtraces（入力・context・tool call・出力）を調べ、実際の障害モードを特定する
  • Bプロンプトこそが最も一般的な原因に違いないという思い込みだけを頼りに、システムプロンプトを最初からまるごと全部書き直してしまう
  • C予防措置として、いったん6か月前のモデルバージョンにまとめてロールバックする
  • Dagentを恒久的に無効化し、ワークロード全体を人手による手作業処理に戻す

A production agent has begun taking unexpected actions on a subset of requests. The on-call engineer’s instinct is to immediately rewrite the system prompt. What should happen first?

  • AInspect the traces of affected sessions — inputs, context, tool calls, outputs — to find the real failure mode
  • BRewrite the entire system prompt from scratch, on the assumption that prompts are usually the most common cause
  • CRoll back to a model version from six months ago purely as a precaution
  • DPermanently disable the agent and return the whole workload to manual processing by staff
✔ 正解 / Correct: A
解説：正答 — (A)：治療の前に診断する。予期しないアクションは、パイプラインのどこからでも生じうる——不正な入力、質の悪い取得 context、誤動作する tool、あるいはプロンプトである。影響を受けた session の traces（入力、取得された context、tool call、出力）を調べれば、実際の障害モードが根拠とともに明らかになり、修正を推測ではなく真の原因に向けられる。これはオブザーバビリティの基本規律であり、まずデータを集めてから行動する。 (B) が不適切な理由：システムプロンプトを一から書き直すのは、「プロンプトが最も一般的な原因」というヒューリスティックで飾った推測にすぎない。根拠なしに動けば、何も直せず、真の原因を覆い隠し、現に動いている挙動を不安定化させる恐れがある。 (C) が不適切な理由：6か月前のモデルへのロールバックは、原因に的中する根拠のない大掛かりで破壊的な介入であり、それ以降のすべての改善を巻き戻してしまう。原因未特定で範囲の限られた問題に対しては影響範囲（blast radius）が大きすぎる。 (D) が不適切な理由：agent を恒久的に無効化するのは、一部のリクエストにしか影響しない障害に対してシステム全体を放棄することであり、範囲の限られた問題を診断して直す代わりに、あらゆる価値を捨てる過剰反応である。
Rationale: Correct — (A): Diagnose before treating. The unexpected actions could originate anywhere in the pipeline — malformed inputs, bad retrieved context, a misbehaving tool, or the prompt. Inspecting the traces of the affected sessions (inputs, retrieved context, tool calls, and outputs) reveals the actual failure mode with evidence, so the fix targets the real cause rather than a guess. This is basic observability discipline: gather data first, then act. Why not (B): Rewriting the prompt from scratch is a guess dressed up as a heuristic ('prompts are the most common cause'). Acting without evidence risks fixing nothing, masking the true cause, and destabilizing behavior that currently works. Why not (C): Rolling back to a six-month-old model is a large, disruptive intervention with no evidence it targets the cause, and it reverts every improvement made since then — a heavy blast radius for an undiagnosed, bounded problem. Why not (D): Permanently disabling the agent abandons the entire system over a failure affecting only a subset of requests — a disproportionate response that forfeits all value instead of diagnosing and fixing a bounded issue.
Q7.2 Domain 7 単一選択Single choice

あるチームは、AIアシスタントを使ってコードの作成とレビューの両方を行っている。AIが作成した変更のレビューではほとんど問題が指摘されないが、それでも欠陥が本番（production）に到達し続けている。レビュー品質を最も直接的に改善する調整はどれか？

  • AAI作成コードは書かれた時点で機械的にチェック済みだという理由で、レビューを省略する
  • Bコードを書いたのと同じsessionに、自分が書いた成果物をもう一度、時間をかけてより注意深くレビューさせる
  • C欠陥が本番コードに決して到達しないよう、AIによる作成をテストファイルに限定する
  • D作成したsessionやagentとは別の新しいcontextでレビューし、merge権限は人間が保持する

A team uses an AI assistant to both write and review code. Reviews of AI-authored changes rarely raise issues, yet defects are still reaching production. Which adjustment most directly improves review quality?

  • ASkip review for AI-authored code, on the grounds it was already machine-checked while being written
  • BAsk the same session that wrote the code to review its own work a second time, but more carefully
  • CLimit AI authoring to test files so that defects can never reach production code
  • DReview from a fresh context — a separate session or agent, not the author — with humans keeping merge authority
✔ 正解 / Correct: D
解説：正答 — (D)：コードを生み出した context と推論を共有するレビュアーは、同じ盲点をそのまま引き継ぐ。元の判断に挑むのではなく、それを正当化・追認しがちになる。これこそが、AIの自己レビューでは「ほとんど問題が指摘されない」のに欠陥が本番に流れ続ける理由である。新しい context からの独立したレビュー（作成時の推論に縛られない別の session や agent）は、本物の批判的な精査を取り戻す。さらに merge 権限を人間が保持することで、出荷されるものに責任を負える人間に説明責任（accountability）が残る。 (A) が不適切な理由：レビューを省略すると最後のチェックを完全に取り除いてしまう。作成時に「機械的にチェックされた」ことはレビューされたことと同義ではなく、レビューを外せば問題は明確に悪化する。 (B) が不適切な理由：同じ session に「より注意深く」再レビューさせても、アンカリング（推論への固着）を繰り返すだけである。2回目も同じ推論から始まり同じ結論に至る。労力を増やしても構造的なバイアスは克服できない。 (C) が不適切な理由：AIの作成をテストファイルに限定すると、AIがコードを書く場所を制約するだけで、問題として挙げられているレビュー品質の改善には寄与せず、本番コードにおける正当な作成価値を不必要に捨ててしまう。
Rationale: Correct — (D): A reviewer that shares the context and reasoning which produced the code inherits the same blind spots. It tends to rationalize and confirm the original decisions rather than challenge them — which is precisely why AI self-review 'rarely raises issues' while defects still ship. Independent review from a fresh context (a separate session or agent, not anchored to the authoring reasoning) restores genuine adversarial scrutiny, and keeping merge authority with humans preserves accountability in a person who can be held responsible for what ships. Why not (A): Skipping review removes the last check entirely. 'Machine-checked' during authoring is not equivalent to being reviewed, and dropping review makes the problem strictly worse. Why not (B): Asking the same session to re-review 'more carefully' repeats the anchoring. The second pass starts from the same reasoning and reaches the same conclusions; more effort does not overcome a structural bias. Why not (C): Limiting AI authoring to test files constrains where AI writes code but does nothing to improve review quality — the stated problem — and needlessly forfeits legitimate authoring value in production code.
Q7.1 Domain 7 単一選択Single choice

あるエンジニアリングリードが、30人のチームにAI支援コーディングツールを展開している。早期導入者がそれぞれツールを異なる設定で構成した結果、コードスタイルが一貫せず、作業の重複が生じている。最も効果的なイネーブルメント（enablement）のステップはどれか？

  • A生産性向上ツールはあくまで個人的な選択だという考えのもとで、各開発者が自分の設定のまま作業をそのまま続けられるようにする
  • B共有・version control管理のプロジェクト設定と標準を確立し、全員のツールに継承させ、個人設定は上に重ねる
  • CAI支援ツールの利用を、チーム内で最も上級のエンジニア2名だけに限定する
  • DすべてのAI生成コードを、commitできるようになる前に手作業で書き直すことを義務づける

An engineering lead is rolling out AI-assisted coding tools to a 30-person team. Early adopters have each configured the tooling differently, producing inconsistent code style and duplicated effort. What is the most effective enablement step?

  • ALet each developer keep their own configuration, on the view that productivity tooling is a personal choice
  • BEstablish shared, version-controlled config and standards everyone inherits, with personal prefs on top
  • CRestrict the AI-assisted tooling to the team's two most senior engineers only
  • DMandate that all AI-generated code be rewritten by hand before it can be committed
✔ 正解 / Correct: B
解説：正答 — (B)：チーム規模では、生産性は「重要なところは一貫させ、そうでないところは自由にする」ことから生まれる。共有され version control で管理されるプロジェクト設定と標準（スタイルルール、共通のプロンプト／CLAUDE.md、再利用可能なワークフローなど）を確立すれば、全メンバーのツールが同じ実証済みのベースラインを自動的に継承する。これにより、各自がばらばらに設定したことで生じた不整合と作業の重複が直接解消される。さらに個人設定をその上に重ねることで、コードベースを分断せずに個々の使い勝手を保てる。これは「アクセラレーター」のパターンであり、実証済みのプラクティスを version control で広めることで、チームが成長しても品質とオンボーディングの両方が改善する。 (A) が不適切な理由：各開発者を自分の設定のまま放置することこそ、まさに現状の問題である。一貫しないスタイルと作業の重複は、管理されない個人設定の直接の症状であり、これでは何も変わらない。 (C) が不適切な理由：ツールを上級2名に限定すると、展開の目的である生産性そのものを捨て、ボトルネックを生む。標準化の問題を「配給制」で答えており、スケールもせず一貫性にも対処していない。 (D) が不適切な理由：AI生成コードをすべて手で書き直させると、生産性の利益を丸ごと捨てて純粋な手間を増やすだけで、痛みの真の原因である設定の不整合には何も対処していない。
Rationale: Correct — (B): At team scale, productivity comes from consistency where it matters and freedom where it doesn't. Establishing shared, version-controlled project configuration and standards — style rules, common prompt/CLAUDE.md files, reusable workflows — means every member's tooling inherits the same proven baseline automatically. That directly removes the divergence and duplicated effort caused by everyone configuring things differently, while layering personal configuration on top preserves individual ergonomics without fragmenting the codebase. This is the accelerator pattern: spread proven practice through version control so quality and onboarding both improve as the team grows. Why not (A): Leaving each developer on their own configuration is exactly the current problem — the inconsistent style and duplicated effort are the direct symptoms of unmanaged personal configs. This changes nothing. Why not (C): Restricting the tooling to two senior engineers throws away the very productivity the rollout exists to deliver and creates a bottleneck. It answers a standardization problem with rationing, which neither scales nor addresses consistency. Why not (D): Mandating a hand-rewrite of all AI-generated code discards the productivity gain entirely and adds pure toil, and it still does nothing about configuration inconsistency — the actual cause of the pain.
Q7.4 Domain 7 複数選択（2つ）Multiple response (choose 2)

あるプラットフォームチームが、運用リスクを持ち込むことなく、組織全体でAI支援開発をスケールさせたいと考えている。この目標を最もよく支えるプラクティスを2つ選べ。

  • A開発の摩擦を一切なくすという理由だけで、すべてのAIツールに無制限の資格情報（credentials）を最初から与えてしまう
  • B開発者が、ツールの生成したAIコードを閲覧・編集することを一切禁止する
  • C共有設定・プロンプト標準・再利用可能なワークフローをversion controlで維持し、チームに継承させる
  • D自動化ツールが実行できる内容を制約する（許可コマンド、protected branches、approval gate）
  • E新しいAI開発ツールを、一般提供が始まった瞬間にすべて即座に採用する

A platform team wants to scale AI-assisted development across the organisation without introducing operational risk. Which TWO practices best support this goal?

  • AGive all AI tooling unrestricted credentials so developers never hit any access friction at all
  • BProhibit developers from inspecting or editing any of the AI-generated code that the tools produce
  • CKeep shared configuration, prompt standards, and reusable workflows in version control to inherit
  • DConstrain what automated tooling may execute — allowed commands, protected branches, destructive-action approval gates
  • EAdopt every newly released AI development tool immediately, the moment it becomes generally available
✔ 正解 / Correct: C、D
解説：正答 — (C) と (D)：AI支援開発を安全にスケールさせるには、アクセラレーター（加速装置）とブレーキの両方が必要である。(C) はアクセラレーター：共有設定、プロンプト標準、再利用可能なワークフローを version control で維持すれば、どのチームも実証済みのプラクティスを自動的に継承でき、採用が広がるほど品質が広まり手戻りが減る。(D) はブレーキ：自動化ツールが実行できる内容を制約すること——許可されたコマンドの一覧、protected branches、破壊的アクションに対する approval gate——によって影響範囲（blast radius）を限定し、ミスを回復可能な範囲に留める。両者を組み合わせることで、運用リスクを抑えつつ速く動ける。 (A) が不適切な理由：無制限の資格情報は影響範囲を最大化する——運用リスクを限定するのとは正反対であり、最小権限にも反する。1回の誤操作や侵害されたアクションが組織全体に損害を及ぼしうる。 (B) が不適切な理由：開発者がAI生成コードを閲覧・編集することを禁止すると、人間による監督——説明責任を人間に残す当の安全装置——を取り除いてしまう。システムはより安全になるどころか安全でなくなり、欠陥を捕まえるレビュー規律も封じられる。 (E) が不適切な理由：新しいツールをリリースと同時にすべて即座に採用すると、変動と未検証のリスクが増え、安全なスケールが依存する安定性と標準化を損なう。運用リスクを持ち込まないという目標とは正反対である。
Rationale: Correct — (C) and (D): Scaling AI-assisted development safely requires both an accelerator and a brake. (C) is the accelerator: keeping shared configuration, prompt standards, and reusable workflows in version control lets every team inherit proven practice automatically, spreading quality and reducing rework as adoption grows. (D) is the brake: constraining what automated tooling may execute — allowed-command lists, protected branches, approval gates for destructive actions — bounds the blast radius so mistakes stay recoverable. Together they let the organisation move fast while keeping operational risk contained. Why not (A): Unrestricted credentials maximise the blast radius — the exact opposite of bounding operational risk — and violate least privilege. A single mistaken or compromised action could do organisation-wide damage. Why not (B): Prohibiting developers from inspecting or editing AI-generated code removes human oversight, the very safeguard that keeps accountability with a person. It makes the system less safe, not more, and blocks the review discipline that catches defects. Why not (E): Adopting every new tool immediately on release adds churn and unvetted risk, undermining the stability and standardization that safe scaling depends on — the opposite of introducing no operational risk.
